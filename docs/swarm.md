# Spot the Swarm: local minimum working detector

The third section of the single-page UI (`/#swarm`), **Explore connections between agents**, uses OpenAI embeddings of authored material and explicit mentions. It requires `OPENAI_API_KEY` and groups agents connected by paths above the selected threshold. See [agent connectivity](agent-connectivity.md) for the formula, evidence API, cache and limits. Connections do not establish bot identity or malicious intent. The existing CPU-only temporal detector remains available through the API described below.

## Try it

Start the backend and Vite using the repository's local startup instructions. During development open http://127.0.0.1:5173/#swarm. After `npm run build --prefix frontend`, the backend serves the same interface at http://127.0.0.1:8000/#swarm. Restart the backend after backend changes unless it was started with reload.

Enter Bluesky links, upload CSV/JSON or paste event rows, then select **Analyze activity**. The old sample-card section and its quick guide are removed from the UI. Existing synthetic fixtures remain available through `GET /api/v1/swarm/examples` for offline/API validation; their labels and detector expectations have not changed.

The interface follows **Add activity → Analyze activity → Read the evidence**. “Group” and “cluster” mean the same thing. The UI uses connected components; the legacy temporal API uses complete-link groups. Data previews are readable without opening the optional raw JSON/CSV editor.

The centered input stays in place during analysis. Results show a compact summary followed by the network map. Expand **Explore evidence** or select a map item to inspect supporting posts below the map. Select a pair to inspect its mention evidence, cosine similarity and normalized line weight. Coverage and method details remain under **Result details**.

For CSV/JSON input, JSON is an array, not a graph. Required fields are `account_id`, `content_id`, `action` and readable `text` or an absolute HTTP(S) `url` for created content. Use ISO 8601 timestamps with `Z` or an explicit UTC offset. `platform` is optional. Reposts, replies, quotes and likes must reference content with a corresponding created observation. Imports are atomic, dataset-scoped, deduplicated and limited to 5,000 rows / 10 MB. Source input and results persist in local SQLite; only import data you are permitted to store.

To analyze real posts without exporting files, expand **Import real posts from Bluesky**, enter public profile URLs, handles or exact post URLs and select **Analyze activity** once. This one action fetches sources, reuses the saved dataset and starts analysis automatically. Profiles use the API's fixed default of at most 50 recent authored posts; there is no cap selector. Each post URL selects the linked post. The UI discovers replies, likes, reposts and quotes on up to ten imported seeds, adds up to 50 new users and fetches up to five recent authored posts each. Added posts never trigger further discovery. Both kinds may be mixed, with duplicate inputs/posts removed. More than 50 unique sources shows an error before any collection request. Readable handles, original-post links and collection coverage stay available alongside the results. A single agent returns `insufficient_data` for pair comparisons. Separately entered or uploaded data cannot be combined with Bluesky links: both inputs stay visible, an error is shown, and analysis is blocked until one is cleared. Changing links clears the old automatic collection preview, not manual input or saved datasets. API requests bypass browser cache; page refresh starts with empty input. Everything stays in this UI. Collection is bounded to one hop; partial results carry coverage warnings. See [the integrated Bluesky guide and earlier experiments](real-data.md) for limitations and API details.

## Legacy temporal API flow

1. `GET /api/v1/swarm/examples`: synthetic input rows with descriptions, never precomputed verdicts.
2. `POST /api/v1/datasets`: `{name, rows}` or `{name, csv}` creates an immutable dataset.
3. `POST /api/v1/swarm/analyze`: `{dataset_id}` returns a queued job with HTTP 202.
4. `GET /api/v1/jobs/{job_id}`: poll until completed, failed, cancelled or interrupted. Queue/run status is separate from the detector's assessment status.
5. A completed job's `result` contains status, warnings, parameters, counts, account labels, pair findings and groups. Episodes include the strongest supporting event IDs, account labels, source text previews, timestamps, lexical similarity and shared URLs.
6. `GET /api/v1/datasets/{dataset_id}/graph` shows content and attributed agents with observed publishing/editing activity or declared capability, connected only by observed actions. Reply metadata adds author-to-parent-post edges in this view; URLs remain post metadata. Coordination findings stay in evidence panels, outside the graph. At most 300 entities are displayed; hidden counts cover the eligible graph. Imports, stored observations and detector results are unchanged.
7. `GET /api/v1/swarm/{dataset_id}/analysis` returns the latest saved analysis. `POST /api/v1/jobs/{job_id}/cancel` cooperatively stops a queued/running job. Failed or interrupted jobs may be explicitly retried through the existing jobs API.

Displaying the network map automatically requests AI content features for its visible posts using the configured OpenAI/TypeSafe keys, with up to two checks at a time. Active posts have blue halos and labels at every zoom level; the progress line separates completed, checking, queued and failed posts. Reduced motion uses steady indicators. This is separate from connectivity embeddings and the CPU-only temporal API. `POST /api/v1/content/analyze` accepts `verification: "none"` for this workflow (existing callers still default to `"sol"`). Compatible successful results are reused and exposed in the graph's `content_screenings` map, including scored posts outside the displayed subset. Reading the graph API alone never starts scoring. Failed checks require **Retry scoring**; posts outside the displayed map can use **Score post** in their evidence cards and share the same queue. Switching graph runs stops local tracking; already submitted server jobs can finish. Saved results use the current screening policy without rerunning models or changing original assessments.

The content-analysis panel also submits entered text to `/analyze` for text-only scoring, with source highlights and feature explanations. It requires the configured provider keys and does not run external verification.

Post and article decisions share five weighted features: logical **30%**, strategic **30%**, emotional **20%**, authority **15%** and repetition **5%**. Missing required emotional/logical/strategic evidence, empty extraction or narrative review produces **Requires further analysis** with a `null` score. Missing optional features are excluded and remaining weights normalized; unknowns never count as zero. With sufficient evidence, below **35/100** produces **Not propaganda**, **35 to below 50** produces **Requires further analysis**, and **50 or above** produces **Propaganda**. The response includes `weighted_score` in 0–1 or `null`, assessment completeness and the policy version; comparisons use unrounded values. Failed requests remain errors. The review label receives a muted amber tint in the map and post cards. These are heuristic bands, not calibrated probabilities. Factual/selective scores remain unassessed without external evidence. Policy changes invalidate graph scoring signatures; saved job/revision reads project current post labels without rewriting history or calling models.

For real Bluesky input, use `POST /api/v1/bluesky/collect` with `actors` and `per_actor` before step 3. It returns a collection job; on completion its `dataset_id` is already persisted, so no separate manual import is needed. The saved source records are available through `GET /api/v1/datasets/{dataset_id}/provenance`. Collected analyses carry collection coverage and readable handles; graph content and matched evidence include original-post URLs.

## Legacy temporal method and boundaries

- Eligible events are created, reposted or replied-to observations with timezone-aware timestamps and at least four distinct text tokens or a valid URL. Likes and derived `links_to` actions are not timing evidence.
- A pair matches within 60 seconds when it shares a URL or at least four distinct tokens with lexical Jaccard similarity at least 0.85. URLs are removed from lexical tokens to avoid bypassing their specificity discount. No URLs are fetched. Query strings are preserved; fragments and default ports are normalized.
- One episode is matching pair activity, extended until there is more than 60 seconds of inactivity. A continuous stream does not accumulate fixed-window "episodes". Evidence belongs to the strongest representative match inside that episode.
- At least three episodes are required. The score combines mean signal strength with excess recurrence over the maximum of eight timestamp-shuffled baselines. Strong pairs need at least two excess episodes and score at least 0.5. Complete-link groups contain at least three mutually strong accounts.
- The sample is insufficient if fewer than two accounts have three eligible events each, or its eligible-event time span is no longer than 120 seconds. Adequate data with no findings is still not proof of safety.
- Comparisons are capped at 500,000 across observed and shuffled runs. Exhaustion, or truncation above 500 returned candidate pairs, withholds all strong assertions. At most 12 representative episodes per pair and 1,200 characters per text preview are returned, with warnings; scores use all counted episodes.
- Missing or unusable observations are counted and warned about. New malformed explicit URLs are rejected at import; malformed URLs in embedded text or legacy data are ignored with warnings rather than crashing the job.
- The shuffle preserves global activity times and account event counts, not each account's rhythms. Eight trials are diagnostic, not statistical significance or calibrated confidence. Fixed seeds and sorted processing make the same dataset reproducible.
- Legitimate scheduling, news sharing, syndication and campaigns can produce coordination signals. Paraphrases and less tightly connected groups may be missed. Precision, recall and false-positive rate have **not** been measured on a real-world benchmark.

This is a local investigation tool. Authentication, per-user abuse protection, data-retention controls, continuous collection, account discovery and deployment hardening remain separate work before public exposure. The integrated Bluesky collector is explicitly initiated and bounded, not a platform-wide crawler.

## Local regression checks

Per the existing repository convention, internal tests are ignored under `.copilot-cache/`. Run `.venv/bin/python -m pytest .copilot-cache/test_swarm.py -q` locally. The suite covers real example outcomes, source-evidence consistency, continuous bursts, abstention, malformed/common URLs, deterministic results, resource limits, cancellation, JSON/CSV imports, saved graphs and persistence across a server lifespan restart. API checks use an isolated temporary database and disable live provider keys.

An independent boundary pass adds `.copilot-cache/test_swarm_boundaries.py`. Run both suites together to include known failure reproductions. The combined result is currently **38 passing and 4 failing checks**, covering three confirmed API input-validation defects. See the [test report](swarm-test-report.md) for reproduction details, browser results and remaining limitations.
